Don't know C++ (2) (inheritance and composition)

My gaps in knowledge have become unbearable. I need to review my understanding of several concepts seriously, from the beginning.

Until I make these ideas clear, I cannot work on other things with peace of mind. Why am I so weak at this?

Chapter 14 of Thinking in C++ opens with this idea:

One of C++’s most important features is code reuse. To go further, however, you need more than copying and modifying code.

This chapter introduces two ways to do that. The first is direct: create an object of an existing class inside a new class. Because the new class is composed of existing-class objects, this approach is called composition.

The second approach is more complex. Create a new class as a type of an existing class. Rather than modifying the existing class, take its form and add code to it. This is called inheritance.

1. Composition syntax

More commonly, the embedded object is made private so it becomes part of the implementation.

2. Inheritance syntax

In code, use the class name as before, but add a colon and the base-class name before the opening brace. For multiple inheritance, list multiple base classes separated by commas. Doing so gives the derived class the base class’s data members and member functions.

Y inherits from X, which means Y contains all of X’s data members and member functions.

All private members of X remain private in Y. Inheritance does not let Y bypass access protection. X’s private members still occupy storage, but cannot be accessed directly.

Also, inheritance is private by default. Without public before the base class, all of the base class’s public members become private in the derived class. That is usually not what we want; use the public keyword to keep them public.

After redefining a function, you may still want to call the base-class version. Calling set() directly invokes the local version and recurses; to call the base class’s set(), explicitly name the base class with the scope-resolution operator.

3. Constructor initializer lists

C++ provides dedicated syntax for calling constructors of subobjects: a constructor initializer list. Its form resembles inheritance syntax. In inheritance, the base class is placed after a colon before the class body. In an initializer list, calls to subobject constructors appear after the constructor’s parameter list and colon, before the function body. 4. Combining composition and inheritance

Although initializer lists often require explicit constructor calls, explicit destructor calls are unnecessary: every type has only one destructor, and it takes no arguments. The compiler still ensures that every destructor is called. Across the hierarchy, destruction begins at the lowest derived layer and continues back to the root.

The program outputs:

As shown, construction starts at the root of the class hierarchy. At each level, the base-class constructor runs first, followed by member-object constructors. Destructors run in exactly the reverse order. This matters because of dependencies: constructors and destructors of a derived class must assume that the base-class subobject is available and has either already been constructed or has not yet been destroyed.

Another important detail: for member objects, construction order is not affected by their order in the initializer list. It is determined by their declaration order in the class. Otherwise, different constructors could establish different construction orders and a destructor would not know which order to reverse, causing dependency problems.

5. Name hiding

Base has overloads of f(). Derived1 does not change f(), so both base-class overloads remain available. Derived2 redefines one version of f() but not the other, so the other overload cannot be used. Derived3 hides both base-class versions by changing the return type, and Derived4 does so by changing the parameter list. In general, when a derived class redefines one overloaded base-class function, every other base-class overload with that name is automatically hidden. The next post explains how virtual affects this.

6. Functions that are not inherited automatically

Not every function is inherited automatically. Constructors and destructors manage object creation and destruction, but each only knows what to do for objects at its own level. Therefore constructors and destructors at every layer must be called: they cannot be inherited and must be created separately for every derived class.

Likewise, operator= cannot be inherited because it performs work analogous to a constructor.
